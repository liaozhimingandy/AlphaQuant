# 数据校验服务：库里缺了什么，缺的那段要不要补

> 配套代码：`app/core/data/integrity.py`（校验器）、
> `app/core/engine/components/dataguard.py`（引擎组件）、
> `app/data/kline_sources.py`（补全走的数据源链路）。

---

## 1. 为什么必须有这一层

**库里缺一根K线，回测不会报错。**

它只是悄悄少一段行情 —— 均线在那几天断开、信号漂移几根、收益差一点点。
没有任何一行日志会说"你少了 2026-09-30 这一天"。这类问题不会崩溃、不会告警，
只会让结论慢慢偏离，是所有数据问题里最难查、也最该被自动化拦住的一类。

常见成因：

| 成因 | 表现 |
| --- | --- |
| 服务昨晚没开 | 最近 1~2 个交易日整段缺失 |
| 采集中途报错（代理抽风、被限流） | 零散缺几天 |
| 停牌 / 退市 | 长期没有数据（**不该补**） |
| 数据源返回了坏行（high < low） | 数据在，但不对（覆盖度统计查不出来） |

## 2. 流程

```
引擎启动 → 组件逐个启动
              │
              ▼
   data_guard 启动（延后 20s，线程池，不阻塞启动）
              │
              ├─ 1. 比对：交易日历算出"应该有哪几天" − 库里实际有的 = 缺口
              │       └─ 右端点锚到**最近交易日**（不是今天）：
              │          否则周日跑一次就凭空多出一个"周日缺口"
              │
              ├─ 2. 判型：缺失占比 > 60% 且 ≥5 天 → 判定停牌/退市，**不补**
              │
              ├─ 3. 补全：fetch_daily() → 走 daily 数据源链路
              │       └─ 权重排序 → 每源重试 N 次 → 换源 → 全挂告警
              │
              ├─ 4. 坏数据扫描：high<low / 价格非正 / OHLC 缺值
              │
              └─ 5. 报告：日志 + /api/dataguard + 组件健康状态
                   之后每 3600s 复查一次
```

**三个刻意的约束：**

1. **不阻塞启动**。体检要查库、可能联网补全，同步跑在 `on_start()` 里
   等于把"引擎起来"押在数据源的脸色上。首检延后 20 秒并丢进线程池，
   这 20 秒也是留给采集服务的：它先把当天数据喂进库，
   校验才不会把"还没来得及采"误判成"缺数据"。
2. **上一轮没跑完就跳过本轮**。补全请求堆积是最容易被限流的；
   漏检一轮无所谓（下一轮还会看到同一个缺口），被封 IP 才是真麻烦。
3. **体检 ≠ 修复**。`auto_repair=False` 时只出报告不联网，
   先看清楚问题再决定要不要补。

## 3. 怎么知道它干了什么

### 日志

```
数据校验服务就绪 | 启动后 20s 首检 | 之后每 3600s 一次 | 回溯 120 天 | 自动补全: 开
数据校验：检查 3 只 | 缺口 2 天 | 已补 2 行
数据补全 | 000001 | 补回 1 行（2026-10-08~2026-10-09，源: baostock_daily）
```

有问题时会打 WARNING（缺数据不会让程序崩，但**必须**留下痕迹 ——
否则"策略最近怎么不准了"永远查不到根因）。

### HTTP API

| 接口 | 说明 |
| --- | --- |
| `GET /api/dataguard` | 最近一次体检报告（缺哪几天 / 补了多少 / 用的哪个源） |
| `POST /api/dataguard/check` | 立刻体检一次。`{"symbol":"600000", "auto_repair": true}` |
| `GET /api/sources` | 数据源权重与健康度（补全用得上哪个源） |
| `POST /api/sources/reset` | 权重与熔断恢复默认（修完代理端口后用） |

### CLI

```bash
alphaquant dataguard                       # 体检（是否补全跟随配置）
alphaquant dataguard --no-repair           # 只体检，不联网
alphaquant dataguard -s 600000 --lookback 30
alphaquant sources                         # 看数据源权重
alphaquant sources --probe --kind daily    # 实测每个日线源通不通（补全前先看这个）
```

### 面板

组件快照里（`data_guard`）有 `report` / `stats` / `auto_repair`，
引擎 `health_check` 会在"仍有缺口未补上"时把它标为不健康。

组件卡片上还会显示**任务进度**：

```text
data_guard            RUNNING
数据完整
数据体检 68 只              62/68 失败 0 进行中
[████████████████████░░]
```

含义是"本轮已检 62 只 / 共 68 只"。体检几十只票要好几分钟，
没有这个进度只能干等，分不清**在跑**还是**卡死**。
进度由 `DataIntegrityChecker.scan(on_progress=...)` 逐只回调驱动，
一轮跑完（或中途抛异常）都会收尾，不会永远显示"进行中"。

## 4. 配置

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `DATA_GUARD_ENABLED` | `true` | 总开关（回测模式自动停用） |
| `DATA_GUARD_START_DELAY` | `20` | 组件启动后多久跑首检（秒） |
| `DATA_GUARD_INTERVAL` | `3600` | 复查周期（秒） |
| `DATA_GUARD_LOOKBACK_DAYS` | `120` | 每只标的回溯多少天找缺口 |
| `DATA_GUARD_AUTO_REPAIR` | `true` | 是否自动补全（关掉 = 只体检） |
| `DATA_GUARD_MAX_SYMBOLS` | `50` | 单次最多查多少只 |
| `DATA_GUARD_MAX_REPAIR` | `20` | 单次最多补多少只（控制请求量） |
| `DATA_GUARD_CHECKS` | `daily,fund_flow,chip` | 校验哪些表 |

命令行：`alphaquant serve --no-data-guard` / `--data-guard --guard-symbol 600000`。

**回测模式默认不启用**：回测读的是历史库，今天缺不缺跟它无关，
而且回测跑完就自动停，体检往往还没开始就被杀了。

## 5. 边界与已知取舍

### 只比对日期与价格，不比对成交量

各源的成交量单位不一致（baostock / 通达信 = 股，akshare / 腾讯 = 手）。
跨源比对成交量必然误报，所以完整性校验**不看成交量**，
详见 `docs/DATA_SOURCES.md`「成交量单位：一个别踩的坑」。

### 停牌票不会被反复补

缺失占比 > 60% 且绝对天数 ≥ 5 → 判定停牌/退市，只记录不补。
否则每轮体检都会去联网补一只停牌票，白打数据源还容易被限流。

### 补全只写缺失的那几天

数据源返回的是一段区间，补全时会**按缺失日过滤**后再入库 ——
否则每次体检都会把区间外的历史行重复写一遍。

### 单只标的的补全失败不影响整轮

失败原因记在 `SymbolReport.error` 里，汇总进 `report.failed`；
整轮体检不会因为一只票连不上源就挂掉。

### 其它表只报告、不自动补

`fund_flow` / `chip` 的"缺口"含义各不相同（资金流没数据可能是停牌，
也可能是没同步），贸然补只会制造噪声。目前只统计行数、标的数、最新日期。

## 6. 手动补一次历史区间

校验服务只管"最近 N 天"的缺口。要补更长的历史，用采集命令：

```bash
alphaquant collect -s 600000 --start 2020-01-01 --end 2026-10-10
```

它走的是 `DataSourceFactory` 那条链路（同一批数据源实现，不含权重/换源）。
两条链路并存的现状见 `docs/DATA_SOURCES.md`。
