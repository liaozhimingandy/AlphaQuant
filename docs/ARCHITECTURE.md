# AlphaQuant 架构与数据流

> 这份文档回答一个问题：**从一根行情到一笔成交，中间到底发生了什么，每一跳由谁负责。**
>
> 建议阅读顺序：先看「一、全景」建立地图，再看「二、数据流闭环」理解一条数据的旅程，
> 然后按需要跳到具体章节。想动手就直奔「七、操作闭环」。

---

## 一、全景

### 1.1 一句话架构

**一个 Twisted reactor 进程 = 一个引擎 = N 个互相隔离的量化任务；
数据从采集流进来，经清洗、指标、因子、规则、策略、风控，变成订单送出去，
成交回报再流回来更新账本 —— 然后喂给下一轮采集，形成闭环。**

### 1.3 三种运行模式的关键差别

同一个引擎、同一套策略代码，靠 `RunMode` 切换运行环境。
**最容易出事的地方就是这张表的第三行**：

| | BACKTEST 回测 | SIMULATE 模拟盘 | LIVE 实盘 |
|---|---|---|---|
| 行情来源 | 历史回放（读完即停） | 实时抓取（poll） | 实时抓取（poll） |
| 撮合 | `SimulatedBroker`，submit 即成交 | 同左 | `LiveBroker`，submit 只是**报单** |
| 成交时机 | 下单那一刻 | 下单那一刻 | **之后的某个时刻**（回报驱动） |
| 持仓更新 | submit 之后立刻 | 同左 | `on_fill` 回调里 |
| 未结订单 | 永远为 0 | 永远为 0 | 会真实存在，可撤 |
| 采集服务 | 装配但停用 | 启用 | 启用 |
| 扩展数据采集 | **不装配**（那段行情是死的） | 启用 | 启用 |
| 券商网关 | 无 | 无 | `LiveGatewayComponent`（必填） |

> ⚠️ **本节最容易踩的坑**：任务级 `run_mode` 默认是"跟随引擎"（空串）。
> 如果代码里硬编码成 SIMULATE，用 LIVE 起引擎时任务仍在模拟撮合 ——
> 面板上一切正常，但**一笔真单都没发出去**。所以 `TaskSpec.run_mode` 默认空串，
> 由 `TaskRuntime.run_mode`（引擎下沉）决定。

### 2.2 为什么"采集 → 清洗 → 存储 → 计算"顺序不能乱

| 顺序 | 如果调换会怎样 |
|---|---|
| 先清洗再入库 | ✅ 正确。库里应该是**干净**的数据，任何读库的路径都不用重复清洗 |
| 先入库再清洗 | ❌ 库里留下脏数据；分钟线尤其致命——重复行会让成交量累计翻倍 |
| 计算时再清洗 | ❌ 每个指标都要重洗一遍；而且策略直接读的是脏数据，等于没有这层 |

### 2.3 为什么"风控前置"必须在仓位计算**之前**

风控拿到的是 `Signal`（意图），不是 `Order`（已定量的单）。
这个顺序决定了风控**无法**精确判断金额——所以：

- 风控层用 `可用资金 × signal.strength` **估算**意图规模（粗粒度早期拦截）
- `LiveBroker` 在拿到最终下单量后做**精确**的金额上限校验（终局拦截）

两层配合：风控层省下一次报单，Broker 层保证不会超。反过来把精确校验塞进风控层，
就得让风控先算仓位——那风控和 sizer 的职责就纠缠在一起了。

### 3.1 引擎组件一览（这就是"服务"的真身）

引擎只认组件，不认业务。所有能力都是组件，按注册顺序启动、逆序停止：

| 组件名 | 文件 | 职责 | 何时装配 |
|---|---|---|---|
| `data_collector` | `components/collector.py` | 定时把行情拉进库 | **总是**（回测模式装配但停用） |
| `ext_data` | `components/extdata.py` | 定时同步资金流/筹码/涨停池/题材 | 非回测默认开（`--no-ext-data` 关） |
| `market_center` | `components/market.py` | 读库/回放 → 发 `BAR_RECEIVED` | 除非外部总线供数 |
| `live_gateway` | `components/live_gateway.py` | 连券商 / 轮询回报 / 定期对账 | 仅 `LIVE` |
| `task_scheduler` | `component.py` | 定时任务与异步任务基座 | 总是 |
| `strategy_manager` | `components/strategy.py` | 持有 TaskRuntime，驱动全部任务 | 总是 |
| `news_center` | `components/news.py` | 抓新闻 → 分析 → 发 `NEWS_ANALYZED` | 可关 |
| `trading_store` | `components/trading_store.py` | 订单/成交/权益/事件落 SQLite | 可关 |
| `monitor` | `monitor/web.py` | 网页面板 + 快照落盘 | 可关 |
| （后台单例） | `monitor/backtest_api.py` | 回测作业：提交 → 线程池执行 → 结果落库 | 随面板 |

**"装配"与"启用"是两个概念**：装配 = 组件挂进引擎（面板能看到、能手动触发）；
启用 = 它的定时器真的在跑。采集服务在回测模式下就是"装配但停用"，
面板会显示"已装配 · 已停用（回测模式只读历史数据，不需要联网采集）"——看得见原因。

## 四、关键设计决策与理由

这一节记录"为什么这么写"。看懂了这些，改代码时才知道哪里不能碰。

### 4.1 阻塞 IO 一律走线程池

采集 HTTP、新闻抓取、LLM 调用、快照落盘、总线读取 —— 全在 worker 线程。
**reactor 线程一旦被阻塞，行情、策略、撮合、面板会一起停摆。**

推论：面板的探测请求也必须跑在工作线程（面板和引擎共用一个 reactor，
在 reactor 线程发 HTTP 会等自己的响应而永久死锁）。真实调用方（浏览器/CLI）
天然是另一个进程，不存在这个问题。

### 4.2 订单事件必须幂等

`StrategyManagerComponent._publish_order` 对 `(order_id, status, filled_size)` 去重。
原因：任务产出的订单会同时经由 `TaskRuntime._emit`（order_sink）和 `on_bar` 返回值
两条路径到达，两处都发布就是**每个订单发两次**。
落库之后成交记录直接翻倍，胜率、成交笔数全部失真。

### 4.3 批内先按主键收敛，单条失败用 savepoint 隔离

模拟撮合是同步的，所以同一个订单几乎**必然**在同一批落库记录里出现两次
（PENDING 然后立刻 FILLED）。而 `session.get()` 在 flush 之前看不到本批新加的行，
两次都会被判成"新记录" → 两次 INSERT → 唯一约束冲突 → **整批回滚**。

不处理的话，一条订单会让同一批里的运行记录、权益点、事件一起消失——
偏偏审计数据是出问题时最需要的。所以：批内去重 + 每条记录一个 savepoint。

### 4.4 实盘：账本拒绝入账时，订单**不能**标成已成交

`Portfolio.apply_fill` 在 `size<=0 or price<=0` 时会返回一条空记录并丢弃。
如果 `LiveBroker` 不看返回值就标记 FILLED，就会出现
**订单显示已成交、持仓却是空的** —— 上层所有后续决策都建立在错误前提上。
正确做法：保留未结状态 + 告警，交给对账兜底。

### 4.5 实时行情与实盘：已有未结订单就不再下单

回测里订单即时成交，这个判断永远为假、零影响；
实盘里订单会挂一会儿，没有这道保护策略会**每根K线都发一单**。
13 根K线就是 13 笔委托，全部成交后建出的仓位远超计划，资金占用完全不可控。

### 4.6 对账必须是账户级的

一个券商账户对应 N 个策略任务。柜台只会告诉你"账户里有 2900 股 000001"，
不会告诉你是哪个策略买的。逐任务拿自己那一份去比账户总额，
除了"只有一个任务"以外**永远对不上**——全是噪音，真差异反而被淹没。
所以 `LiveGatewayComponent` 把所有任务的持仓/资金汇总后与券商比一次。

### 4.7 快照"有操作才写"，不是"到点就写"

**先分清两件被混为一谈的事**：

| | 触发者 | 落磁盘？ |
|---|---|---|
| 面板轮询（默认 2s） | 浏览器 `setInterval` | **不落盘**，读引擎内存状态 |
| 快照落盘 | 引擎状态变更 | 落 `output/snapshots/<run_id>/` |

默认模式 `on_event` 的触发源是一份**白名单事件**（`TRIGGER_EVENTS`）：
下单/成交/撤单/拒单、任务增删改暂停恢复、组件启停、控制指令。
**`BAR_RECEIVED` 刻意不在里面** —— 把行情放进去就等于回到"行情一动就写盘"，
而行情自己跳动、权益随之浮动**不构成状态变更**（那是同一份状态的不同读数）。

一次回放可能在一秒内产生上百笔订单，逐个写盘纯属浪费。所以有两条合并闸：

- `snapshot_debounce`（默认 1s）：操作后等一小会儿再落盘，同一批操作并成一份
- `snapshot_min_gap`（默认 2s）：两次落盘的最小间隔

实测：冒烟里 15 次操作只落 3 份快照。按时间写的话同样的过程会产生 15 份、
其中大部分内容完全相同。

另外两个模式仍然保留：`on_change`（定期查指纹，覆盖"状态自己漂移"）、
`interval`（要完整时间轴时）。指纹计算剔除时间戳/序号/内存等易变字段，
只比**状态本体** —— 不剔除的话"变了才写"永远成立，等于没做。

> 踩过的坑：阈值型开关里 `snapshot_enabled=None` 表示"用默认"，
> 但代码里 `if snapshot_enabled else` 会把 None 当假值，日志于是写"快照关"
> 而实际开着。**"看起来是关的其实开着"这类日志比没有日志更害人。**

### 4.8 券商接入点：网关类型 ≠ 资金账号

`BROKER_GATEWAY=simulated` 回答的是"用哪种网关实现"，没回答"连谁"。
真实场景里模拟托盘/实盘主账户/实盘小号/备份通道是**同一网关类型、不同接入点**。
把账号写死在代码或环境变量里，切换成本高，而且**容易连错账户**。

`config/brokers.json` 把"网关 + 资金账号 + 连接参数"打包成命名接入点：

- **凭据只写"从哪个环境变量取"**（`credential_env`），所以配置文件可以入库；
  面板/CLI 显示的都是打码值（`mask_secret`）
- 显式指定的接入点找不到会**直接报错**，不静默降级到别的账户
- 接入点的字段按网关构造签名**过滤**后再传（`filter_kwargs`），
  不会因为"多配了一个字段"就 `TypeError` —— 那是接新券商时最容易踩的坑
- `readonly: true` 是首次接入的推荐档位：能查账户/持仓/收回报，但不下单

**实盘账户从券商源读**：`LiveGatewayComponent.refresh_account()` 定期
（默认 30s）查一次资金/持仓并缓存到内存。面板每 2 秒刷新一次，
不可能每次都去问券商（那是秒级网络 IO 且有频率限制）。

### 4.9 SQLite 必须开 WAL 并把等待时间放宽

`app/db/database.py` 在连接时设 `journal_mode=WAL`、`synchronous=NORMAL`、
`busy_timeout=30000`。

不是"优化"，是**必须**：本项目同时有

- 后台线程批量落库（`TRADE_FLUSH_INTERVAL`，默认 2s 一批）
- 面板/CLI 随时查询（`ctl db orders` 之类）

默认的 rollback-journal 模式下，读会拿到共享锁并把写挡回去；默认 5 秒的
`timeout` 在磁盘慢的机器上完全不够，于是报 `database is locked` ——
**看起来像代码 bug，其实只是等得太短**。WAL 让读写互不阻塞，30 秒等待兜住抖动。

### 4.10 指标周期是参数不是指标

`sma` 只有一个，周期靠 `ctx.ind("sma", period=20)`。注册 `sma5/sma10/sma20`
会让注册表爆炸、缓存失效、策略配置无法复现。

指标结果缓存挂在 `BarSeries` 上，用 `revision` 判断失效 ——
**不能用 `len()`**：`deque(maxlen=N)` 满了之后长度恒为 N 而内容在往前滑，
只看长度会读到"上一根K线"的指标值，是**静默的错误信号**。

### 4.11 日志分级：默认只记重要的

| 级别 | 记什么 |
|---|---|
| INFO（默认） | 生命周期、成交、风控否决、采集结果、异常 |
| DEBUG | 逐根K线决策、缓存命中、指标中间值 —— **只在排查问题时开** |

两条防膨胀措施：文件级别可单独设得更严（`LOG_FILE_LEVEL`）；
同一位置的重复日志按时间窗节流，窗口结束时补一条"被压缩了多少次"——信息不丢，只是不重复。

### 4.12 周线因子必须逐根因果

站在周三时，"本周"的代表价应该是**周三自己的收盘**：

- 用上一周的值 → 整周滞后，金叉信号晚一周
- 等周五再算 → 滞后到周末
- 偷看本周周五 → **未来函数**，回测赚的钱实盘一分拿不到

`weekly_ma_check.py` / `weekly_factor_check.py` 用独立参照实现交叉验证（偏差 1e-14）。

### 4.13 自定义策略：回测链路与实盘链路共用一套发现机制

项目里有**两套策略接口**，因为它们运行在完全不同的引擎上：

| 链路 | 基类 | 引擎 | 为什么不能用同一个 |
|---|---|---|---|
| 回测 | `backtrader.Strategy` | `cerebro` | backtrader 自带撮合/指标/分析器，重写代价太大 |
| 实盘/模拟 | `IBaseStrategy` | 本项目事件引擎（Twisted） | 需要回报驱动、T+1、账户级对账 |

但**发现机制是同一套**（`app/core/strategy/discovery.py`）：
扫描目录 → 按文件路径指纹导入模块 → 从模块里挑出各自基类的子类 → 按
`STRATEGY_NAME`（缺省由类名推导）注册。

这样用户可以把同一个想法写成两个类放进一个文件，回测验证过的参数直接用于实盘 ——
而不是"回测里用 5/20，实盘里手滑写成 5/30"。

三个刻意的设计：

1. **单个文件加载失败只跳过它并记日志**。一个写坏的策略不该让整个程序起不来。
   但一定要报出来，否则用户会以为"我的策略没被发现"。
2. **模块名带路径指纹**。不同目录下的同名文件必须互不覆盖 ——
   否则后加载的顶掉先加载的，排查起来莫名其妙。
3. **注册名优先用显式声明的 `STRATEGY_NAME`**。类名一改，配置文件里的引用就断了，
   而显式名字是稳定的。

**声明式策略 `declarative`** 是给"不写代码"的场景准备的：它把项目自己的
因子/规则层接到 backtrader 上（每根K线重建 `BarSeries` → `FactorContext` → 求值规则），
所以**回测和实盘用的是同一套判据**，口径不会漂。规则没配时用默认的 5/20 均线交叉，
但会在日志里明确说"现在跑的是默认规则"。

### 4.14 回测默认值必须有单一来源

初始资金、手续费、滑点、默认区间这类**业务参数**会变，但它们曾经散在三处：
CLI 的 `click` 默认值、面板 HTML 里的 `value="100000"`、作业 API 的硬编码。
三份迟早不一致，于是"命令行跑出来"和"面板跑出来"结果不一样，还很难查。

现在只有 `config/backtest.json` 一个来源，CLI / 面板 / 作业 API 都读它。
优先级：**显式传入 > 配置文件 > 内置兜底值**。
`BacktestDefaults.merge()` 还特意规定"空值不覆盖默认"——面板表单里没填的
字段就是这样传上来的（`None` / `""`），直接覆盖会把默认值冲掉。

### 4.15 截面数据必须和K线数据分开采集

资金流、筹码分布、涨停池、题材归属是**日频截面**数据，一天一只票只有一条；
K线是**时间序列**，一天一只票有几十~几百根。两者的粒度、频率、失败语义全不一样：

| | K线采集（`data_collector`） | 扩展数据（`ext_data`） |
|---|---|---|
| 粒度 | 逐根K线 | 每日一条（资金流/筹码）+ 市场级快照（涨停池/题材） |
| 频率 | 分钟级 | 10 分钟（个股）/ 1 小时（市场级） |
| 重试语义 | 抓失败下次再抓即可 | 抓两次是纯浪费；涨停池一次就覆盖全市场 |

硬塞进同一个组件会让两边都难懂，所以是独立的 `ExtDataComponent`。
它还有一条硬规则：**采完新数据后必须让 `FeatureProvider` 缓存失效**，
否则策略会一直拿着几小时前的资金流在打分 —— 面板看着在跑，分数其实是旧的。

### 4.16 缺维度要重新分配权重，不能按 0 分算

一只票可能没有题材归属（不在任何热门板块里），也可能没有筹码数据。
如果把它当 0 分参与加权，结果就是"没数据的票被系统性低估"，
而真正的问题只是**数据缺失**，不是"这只票很差"。

`ScoreEngine` 的做法是：先算出哪些维度可用，**只在可用维度之间重新归一化权重**，
然后在 `reasons` 里写明"题材维度无数据，权重已重新分配"。
这样 60 分是"各方面都一般"，和"只有两个维度有数据但都很好"能区分开。

### 4.17 数据缺失时因子必须返回 `None`，不能返回 0

`main_net_pct`（主力净流入占比）缺数据时返回 `None`，不是 0。
这条看着小，实际上决定了策略能不能正确降级：
返回 0 的话，"没数据"和"资金持平"在下游完全无法区分，
打分会被一堆假 0 拉平。**缺失就是缺失，不要用 0 假装知道。**

### 4.18 先收窄候选池，再精细打分

全市场 5000 多只票逐只拉资金流+筹码，既慢（几十分钟）又必被限流，而且没意义 ——
绝大多数票根本不在关注范围内。所以是两段式：

```
候选池（涨停池 / 热门题材成分 / 自选 / 资金流排名）
        │  几十~几百只
        ▼
同步数据 → 多维打分 → 排序 → 落库 → 推荐
```

还有一条防线：**候选池拉失败时返回空列表，绝不退化成全市场**。
"拉不到"和"池子很大"是两回事，静默退化会把一次几十秒的操作变成几十分钟，
而且用户完全不知道发生了什么。

### 4.19 模拟网关的本金要以任务为准，且每个任务只计一次

券商账户是**一个**，本地是 N 个任务各有一本账，所以对账时券商侧本金必须等于
所有任务本金之和。模拟网关没有真实券商可问，只能由任务挂载时把本金累加进它的账本。

这里踩过两次坑，两次的表现都是"对账不一致 → 严格模式阻断交易"：

1. **接入点配置里的 `initial_cash` 被叠加**。`config/brokers.json` 的 `sim` 接入点
   自带 `initial_cash: 100000`（那是给"单独用网关"场景兜底的）。直接往上累加，
   就变成"本地 28 万、券商 38 万"。所以**第一个任务挂上来时先清零** ——
   一旦有任务，任务本金就是权威来源，接入点的默认值必须让位。
2. **同一个任务被挂两次**。装载阶段和启动阶段都会走一遍挂载，
   本金于是被计两遍。按 `task_id` 去重，只有第一次计入。

真实券商网关不在这条路径上（它的资金以券商为准，绝不能被本地覆盖），
代码里用 `gateway.name == "simulated"` 严格区分。

### 4.20 闭市不请求：交易日历是一等公民

"什么时候能采"和"采什么、多久采一次"是平级问题，不是散落在组件里的 if。

以前判断交易日的逻辑是"周一到周五"，于是国庆那七天里有五个工作日
照样在每 10 分钟请求一次数据 —— 请求发出去了、限流风险占了、日志刷了一屏，
拿回来的还是和上一交易日一模一样的数据。更糟的是它掩盖真问题：
日志里"一切正常"，实际一天里绝大多数请求都是无意义的重复。

现在统一由 :mod:`app.core.market.calendar` 判断，分三层兜底：

1. **内置表** —— 已公布的交易所休市安排（2025 / 2026 精确到日）
2. **配置文件** —— `config/trade_calendar.json`（联网校准后写这里，之后离线可用）
3. **联网刷新** —— `main.py calendar refresh`，失败**不动现有日历**

最后一条是关键：日历缺失会导致"该采的时候不采"，
那比多采几次严重得多，所以宁可用旧的，也绝不因为刷新失败就清空。

日频截面数据（资金流/筹码/基本面）另外还有一条约束：**一天只采一次**。
它一天里只有"盘中波动"和"收盘定稿"两种状态，盘中采一次、收盘后补一次定稿，
其余时间一次都不请求。

### 4.21 基本面是过滤器，不是择时器

基本面（估值/成长/质量）是**慢变量**：一份财报要用一个季度。
所以它不该有高权重 —— 给它 40%，打分结果会被几个月前的数据主导，
而选股要的是"现在谁在被资金推动"。项目里给它 12%，定位是**过滤器**：
把垃圾股挡在池子外面，而不是决定排名先后。

两个容易写错的地方：

- **`report_date` 必须单独记**。用"采集日"标记一份三季报，
  回看时会误以为当时就知道了 —— 这是最隐蔽的一类未来函数。
- **PE 为负（亏损）是确定的坏消息，不是"没数据"**。
  所以风控里它可以拦，而缺失的 ROE 不行。

基本面算分只有**一份实现**（`app.core.data.features.fundamental_score`），
因子、特征注入、风控闸门三处共用 —— 三处各写一份，迟早算出三个不同的分数。

### 4.22 因子是策略的核心，所以因子必须能被"积累"和"验证"

（这一条来自 Qbot 的设计理念：策略是量化的核心，因子是策略的核心。）

落到本项目是三件事：

1. **写因子不该有摩擦** —— 表达式因子（`app/core/factor/expr.py`）：
   写一句 `close / MA(close, 20) - 1` 就是一个因子，界面上就能加。
   用自写的 tokenizer + 白名单函数表，**不用 eval**：
   表达式来自输入框，eval 等于给它一个任意代码执行的口子。
2. **因子要能沉淀** —— 因子库（`config/factors.json`）：
   加载即注册，规则/策略/回测/面板都能直接引用。没有库，研究就没有复利。
3. **因子要能证伪** —— 检验（`app/core/factor/evaluate.py`）：
   IC / RankIC / ICIR / 分层单调性 / t 值。**没有判据就谈不上自动挖掘**。

三个必须守住的坑：

- 所有算子都是**因果**的。RANK 是"截至当前"的扩展窗口百分位，
  不是全样本排名 —— 后者用未来数据给历史打分。
- 截面 IC 才是"这个因子能不能区分好坏"。时间序列上会被趋势主导
  （牛市里几乎所有因子都显得有效）。标的 < 3 时退到时间序列口径，
  但**必须在结论里写明口径更弱**。
- 挖掘出来的因子绝大多数是**过拟合**的。所以默认不入库，
  入库也要标 `source=mined`，出了事知道该怀疑谁。

### 4.23 机器学习只做两件事：筛因子、配权重

不追求模型复杂度 —— 环境只有 numpy/pandas，且因子层面的任务
本质上就是线性模型。

- **Lasso（坐标下降）**：L1 惩罚把无用因子权重压到 0，
  这正是"从 50 个候选里挑 8 个"。岭回归只会缩小权重、一个都不删，
  所以不适合用来**筛**。
- **先去共线再拟合**：高度相关的两个因子，Lasso 会**随机**留一个。
  不先剔除，你以为是模型选出来的，其实只是它先撞上了哪个。
- **惩罚强度用验证集选**（从训练段里再切最后 20%）。
  直接拿测试集调参是最常见的自欺，调完的"样本外"其实已经被污染。
- **按时间切分**，不打乱：随机切分会让训练集里出现未来。

### 4.24 通用因子值表：让"新增数据维度"只改一处

```
stock_factor_value(symbol, date, category, name, value, extra_json)
```

要接的类别会不断加（龙虎榜、两融、业绩预告、股东户数、机构评级、
研报、大宗交易、北向持股……）。如果每加一类就建表 + 写仓储 + 写查询，
三个月后就是十几张**结构完全相同**的表和十几套几乎一样的代码 ——
而它们本质上都是 (标的, 日期, 指标名, 数值)。

统一成一张表之后：

- 新增一类数据 = 加一个获取函数，**不动表结构 / 仓储 / 查询**
- 特征层一次性把所有类别装配起来（`category` 只是个标签）
- 指标名是数据驱动的，界面能列出"现在库里有什么"

代价是数值只能是 float（放不下的进 `extra_json`）、没有列级约束。
对截面因子数据来说这是划算的交换。

三类数据**例外**，仍各自成表：

- 新闻/公告（`market_news`）：带标题与情感分，不是纯数值
- 宏观（`macro_indicator`）：市场级，没有 symbol
- 市场宽度（`market_breadth`）：市场级，字段语义固定

### 4.25 宏观与市场宽度是"环境开关"，不是选股维度

这两类对所有标的同值，所以：

- **不参与票与票之间的排序**（所有票一样，排序没有意义）
- 只用来回答"现在整体该进攻还是防守"

宏观不能预测明天涨跌，但它决定**哪类策略在这个环境下能活**：
利率上行 → 高估值成长股承压；PMI 拐点 → 周期股领先。

所以权重刻意压到 0.06。给高了会稀释掉真正的选股信息 ——
那是把"今天天气不错"当成了"这只票值得买"。

### 4.26 策略要能在界面上改，否则没人会去调

策略存成**声明式配置**（`config/strategies.json`）而不是代码：

```
改一个阈值 = 改一个数字 + 保存（不用碰 .py、不用重启）
```

为了把 30 改成 35 去改 Python 文件再热加载，摩擦太大 ——
最后的结果就是策略一旦写完就再也不动。需要写复杂逻辑时
仍然去 `strategies/` 写 Python，两条路径并存。

两条硬约束：

- 保存时**结构校验**（`exit_score ≥ entry_score` 直接拒绝并说明原因），
  而不是等上线运行时才发现（那时可能已经在真金白银地下单了）
- 上线时若没配风控，自动补一条 `max_drawdown` —— 用户常常忘记配

### 4.27 采集时间窗口：盘前补齐 + 盘后定稿

默认两个窗口（都可在配置文件与面板里改）：

| 窗口 | 时刻 | 采什么 |
| --- | --- | --- |
| 盘前 | 开盘前 30 分钟（9:00） | 补齐昨日漏采、预热当日标的 |
| 盘中 | 9:30–15:00 | **只采分钟级**；日频截面默认不采 |
| 盘后 | 闭市后 30 分钟（15:30） | 当日**定稿**数据 |

两个关键判断：

- **15:00 整去拉拿到的是未定稿数据**。交易所与数据源需要结算时间，
  当天资金流、涨停池此刻都还在变。早了拿到脏数据，晚了白白等待。
- **日频截面数据盘中反复拉是浪费**。一天一条的东西拉十次拿到的
  基本是同一个数，还会把自己送进限流名单。所以 `intraday_enabled`
  默认关闭 —— 这个开关打开前请确认真的需要。

盘后窗口必须有**宽限时长**（默认 120 分钟）。否则凌晨 3 点
也会自认为"在盘后窗口"而去请求当天还没有的数据。

### 4.28 因子要能被"看见"才谈得上被使用

注册表里 60+ 个因子，如果界面只列出其中 8 条（因子库里的表达式因子），
用户就会以为系统只有这几个可用 —— 于是题材、基本面、资金、舆情、
宏观那几十个从来没被用过。**因子的价值在于被用起来，不是被列出来。**

所以面板按类别分组展示全部因子（量价/表达式/题材/筹码/资金/基本面/
舆情/宏观），并且标注**库里有没有数据**。

最后一项最关键：很多人写完策略发现"怎么一直没信号"，
查半天才发现那个因子压根没采过数据，用了也只会得到 None。

## 五、观测体系：三种数据各司其职

不要混用，否则要么查不动、要么丢历史：

| | 内存（面板） | SQLite | 快照文件 |
|---|---|---|---|
| 存在哪 | 引擎进程内存 | `data/alphaquant.db` | `output/snapshots/<run_id>/` |
| 何时写 | 不写（直接读） | 事件驱动 + 定期采样 | **有操作时**（`on_event`，可切换） |
| 适合回答 | "现在什么状态" | "某天某任务成交了哪些笔" | "那一刻整体长什么样" |
| 能按条件查吗 | 不能 | ✅ 索引 + 聚合 + join | 不能（顺序读） |
| 重启后还在吗 | ❌ | ✅ | ✅ |
| 会被清理吗 | —— | 长期保留 | 滚动保留 N 份 |

**选择口径**：需要"筛一批行/做聚合"→ 查 SQLite；需要"看当时的完整快照"→ 读快照文件。

```bash

python main.py ctl db trades --task-id ma-000001    # 某任务的成交明细
python main.py ctl db equity ma-000001              # 权益曲线
python main.py ctl db events --category risk        # 风控类事件
python main.py snapshot --tasks                     # 最近一次运行的整体快照
```

### 7.4 出问题时的排查路径

| 现象 | 先看哪里 |
|---|---|
| 面板显示"未启用" | `ctl overview` 看组件状态；采集停用会带原因 |
| 任务在跑但不下单 | `ctl db orders --status REJECTED` 看是否被风控否决；`ctl db events --category risk` |
| 实盘下单了但持仓没变 | `ctl live status` 看 `unknown` 回报数；确认任务已挂到网关 |
| 连的账号不对 | `ctl endpoints list` 看"使用中"那个；`ctl live account` 看账号 |
| 连不上券商 | `brokers check <endpoint>` 单独试；看它报的是网关未注册还是凭据缺失 |
| 实盘对账不一致 | `ctl live reconcile` 看持仓/资金差异；检查是否有人工交易 |
| 回测赚钱实盘亏钱 | 检查 `t_plus_one` / `price_limit` 是否启用；检查是否有未来函数 |
| 回测结果和以前不一样 | `backtest --show-defaults` 看默认参数是否被 `config/backtest.json` 改过 |
| 自定义策略没出现在下拉框 | `ctl strategies --reload`；看日志里有没有"加载用户策略 xxx 失败" |
| 数据看起来不对 | `ctl db events --category collect`；日志里搜"清洗" |
| 磁盘涨得快 | `ctl snapshot-mode on_event`（默认）；`LOG_LEVEL` 别开 DEBUG；调 `EQUITY_SAMPLE_INTERVAL` |
| 快照太多 / 以为在按秒写 | `ctl snapshot-mode` 看是哪个模式；顶栏刷新频率 ≠ 快照频率 |
| 日志刷屏 | 日志有重复节流；确认 `LOG_LEVEL` 不是 DEBUG |

## 八、设计约束速查（踩过坑才写在这里）

按主题分组，每条都是"改了会出真问题"的地方。

**交易正确性**
1. 风控只能否决、不能下单。强制平仓放在 `QuantTask._check_max_hold`。
2. 卖出量不允许超过持仓。`Portfolio.apply_fill` 二次截断，杜绝净做空。
3. 已有未结订单时不再下单（实盘防堆单）。
4. 账本拒绝入账时订单不能标成已成交。
5. 成交回报必须幂等（券商可能重复推送）。
6. 部分成交的日内计数用**累计量差值**，不能"成交一次加一次"。
7. T+1 的 `bought_today` 必须跨日归零，否则第二天所有卖出都会被误拦。

**实盘**
8. 一个券商账户 N 个策略 → 对账必须账户级。
9. 网关共用一条连接（券商不允许同账号多连接）。
10. 撤单是异步的：返回 True 只代表受理，状态要等回报。
11. 下单通信失败 ≠ 没下出去。状态留 SUBMITTED 去对账，**绝不能重发**。
12. 停服务前先撤单，否则会留下"孤儿单"第二天开盘才成交。
13. 连不上券商是致命错误，必须让引擎起不来（不能假装在交易）。

**数据**
14. 采集不能全量重下：前复权价格会因除权除息整体重算，必须回看一个窗口。
15. 上一轮没跑完就跳过本轮（慢网络下堆积请求会导致雪崩式限流）。
16. 清洗默认只标记不丢弃（丢不可逆，且分不清真异常和没想到的合法情况）。
17. 没有价格的行是唯一必须丢的。

**工程**
18. 阻塞 IO 必须走线程池。
19. 枚举序列化要在基础类型之前判断（`class Side(str, Enum)` 会先命中 `str`）。
20. 状态采集与落盘必须分线程（否则任务增删时字典迭代会炸）。
21. 指标缓存不能用 `len()` 判断失效（deque 满了长度不变）。
22. 构造参数不能与基类方法同名（`self.size = ...` 会覆盖 `size()`）。
23. 定时器只能在组件 RUNNING 时起，否则同频率会出现两个定时器。
24. 进程退出只认停止标记文件（Windows 没有 SIGTERM）。
25. venv 的 `python.exe` 是壳，`Popen.pid` 不等于引擎 PID。

**可观测与配置**
26. 快照只能由"操作"触发，`BAR_RECEIVED` **不能**进触发白名单。
27. `snapshot_enabled=None` 表示"用默认"，不能当假值用（会写出骗人的日志）。
28. 接入点的凭据只存环境变量名；面板/CLI 一律打码输出。
29. 显式指定的接入点找不到要**直接报错**，不能静默降级到别的账户。
30. 接入点参数要按网关构造签名过滤，不能原样透传（多一个字段就 TypeError）。
31. 券商账户查询要缓存（秒级 IO + 频率限制），不能每次面板刷新都问一遍。
32. 回测默认值只能有一个来源（`config/backtest.json`），且空值不覆盖默认。
33. 用户策略加载失败只跳过该文件，但**必须记日志**。
34. SQLite 必须开 WAL + 放宽 busy timeout（并发批量写 + 面板读）。
35. `load()` 式的惰性初始化不能用 `if 容器非空: return` 做守卫 ——
    先注册用户扩展会让内置项永远补不上（内置策略曾因此全部消失）。
36. 截面数据（资金流/筹码/题材）只能**按天**对齐，不能 ffill 到分钟级 ——
    那是拿未来一天的信息去解释当天的分钟K线。
37. 因子缺数据必须返回 `None` 而不是 0（见 §4.17），
    否则"没数据"和"数值为 0"在下游无法区分，打分会被一堆假 0 拉平。
38. 采完截面数据后必须让 `FeatureProvider` 缓存失效，
    否则策略一直拿着几小时前的资金流打分（见 §4.15）。
39. 从库里读出来的评分字典必须同时给 `total` 和 `total_score` ——
    库列名叫前者，打分引擎和面板用后者，只给一个会出现
    "明细里有分、列表里全是 0" 的怪象。
40. 模拟网关的本金只能由任务本金累加一次（见 §4.19）：
    接入点自带的 `initial_cash` 必须先清零，且同一任务重复挂载要去重。
41. 闭市不请求数据（见 §4.20）。判断交易日**不能只看是不是周末** ——
    国庆七天里有五个工作日。日历刷新失败时沿用旧日历，绝不因缺日历就不采。
42. 日频截面数据一天只采一次（盘中一次 + 收盘定稿一次），
    盘后反复拉涨停池/基本面纯属浪费请求额度。
43. 基本面算分只能有一份实现，因子/特征注入/风控三处共用（见 §4.21）。
44. 财报的 `report_date` 必须单独记。用采集日标记三季报 = 未来函数。
45. `min_score` 风控**只拦买入**：卖出被评分挡住等于逼人扛着亏损单。
46. 因子表达式**不能用 eval**求值（来自界面输入框 = 任意代码执行）。
47. 因子算子必须因果：RANK 用"截至当前"的扩展窗口，不是全样本排名。
48. 机器学习的惩罚强度只能用**验证集**选；用测试集调参是自欺。
49. 挖掘的因子默认不入库存；入库必须标 `source=mined` 并带上检验指标。
50. 新增数据类别 = 加一个获取函数，**不动表结构**（见 §4.24）。
51. 宏观/市场宽度对所有票同值，只能当环境开关，权重必须压低（见 §4.25）。
52. 通用因子值读"不晚于 day 的最近一条"，不是"恰好等于 day" ——
    股东户数、机构持仓这种慢更新数据按天精确匹配会永远查不到。
53. 市场级数据（宏观/宽度）要在特征层**按时间缓存**，
    否则给 500 只票打分就查 500 次同一行。
54. 策略保存时要做结构校验；上线时自动补 max_drawdown 兜底。
55. 采集默认只在**盘前 30 分钟**与**闭市后 30 分钟**两个窗口；
    15:00 整拉到的是未定稿数据（见 §4.27）。
56. 盘后窗口要有宽限时长，否则凌晨也会自认为在窗口内。
57. 界面必须展示**全部**因子并标注数据可用性，不能只列因子库里的（见 §4.28）。
58. 因子注册表里**不能有同名重复注册** —— 覆盖顺序取决于谁先被 import，
    那是"重启一次行为就变了"的经典来源。

## 十、资金流因子 · 多维度打分 · 股票池

这是量价之外的一套**独立信号源**。K线只告诉你"价格怎么走的"，
资金流告诉你"谁在推动它" —— 同样是涨 5%，主力持续净流入和散户情绪拉抬，
后续的持续性完全不是一回事。

### 10.1 数据链路

```
akshare 日频截面源
   │  app/data/marketx.py      封装 + 失败降级 + 节流
   ▼
app/core/pool/sync.py          同步编排（单只失败不影响其它）
   ▼
SQLite 表                      FundFlow / ChipDistribution / LimitUpPool
   │                           ThemeFlow / StockTheme / StockScore
   ▼
FeatureProvider               app/core/data/features.py
   │  读库 → 装配成特征字典 → 注入 FactorContext（TTL 缓存 300s）
   ▼
Factor                        app/core/factor/flow.py
   │  main_net_pct / capital_accel / capital_pulse / net_inflow_days
   │  chip_profit_ratio / chip_concentration / chip_peak_gap
   │  theme_rank / theme_pct / limitup_effect / composite_score
   ▼
ScoreEngine                   app/core/score/engine.py
   │  资金 / 题材 / 筹码 / 技术 / 涨停 加权 → 总分 + 等级 + 扣分理由
   ▼
StockPool                     app/core/pool/pool.py
      候选池 → 打分 → 排序 → 落库 → 推荐
```

**采集节奏是刻意分层的**（都在 worker 线程，全是同步 IO）：

| 数据 | 范围 | 默认节奏 | 理由 |
|---|---|---|---|
| 资金流 / 筹码 | 按标的 | 盘中一次 + 收盘定稿一次 | 一天一条，抓两次是浪费 |
| 基本面（估值+财务） | 按标的 | 收盘后一天一次 | 季频数据，一天拉 100 次拿到的是同一份财报 |
| 涨停池 | 市场级 | 一天一次 | 收盘后即定稿 |
| 题材板块 / 成分映射 | 市场级 | 一天一次 | 归属变化很慢 |

**闭市一次都不请求**（见 §4.20）。判断由交易日历统一负责：
内置已公布的交易所休市安排 → `config/trade_calendar.json` → 联网校准，
三层兜底，且刷新失败绝不清空日历。

### 10.2 五个维度在量什么

| 维度 | 回答的问题 | 主要依据 |
|---|---|---|
| 资金 `capital` | 有大资金在进吗？进了多久？在加速吗？ | 主力净流入占比、加速度、连续净流入天数 |
| 题材 `theme` | 它站在当前主线上吗？ | 所属题材的排名与涨幅 |
| 筹码 `chip` | 上方套牢盘重不重？ | 获利盘比例、集中度、与筹码峰的距离 |
| 技术 `technical` | 形态本身走坏了吗？ | 既有量价因子 |
| 涨停 `limitup` | 涨停是"硬板"还是"烂板"？ | 连板数、封单额、炸板次数合成的涨停效应 |
| 基本面 `fundamental` | 这家公司值不值得买？ | PE/PB/ROE/毛利率/营收与净利同比/负债率/股息率 |

基本面是**过滤器不是择时器**（见 §4.21）：它几个月才变一次，
权重给到 12%，作用是把垃圾股挡在池子外面，而不是决定排名先后。

风险项**只扣分不加分**（比如连续暴涨后的位置风险），
这样"分数高"永远意味着"各维度都好"，而不是"某一项特别猛把总分拉上去了"。

权重在 `config/score.json` 里，改配置即可，不用改代码。
缺维度时权重会在可用维度间重新归一化（见 §4.16）。

### 10.3 怎么用

```bash
# 打分明细（某一只票，逐维度看）
python main.py score 600000

# 资金流与筹码原始值
python main.py flow 600000 --days 10

# 刷新股票池（拉候选 → 同步 → 打分 → 落库）
python main.py pool refresh --source limitup --limit 30

# 看已保存的推荐（离线可用，不联网）
python main.py pool top --limit 20

# 单独同步某一类数据（不打分）
python main.py pool sync fundflow --symbol 600000

# 本机无网络时先跑这个：造合成数据验证打分与排序链路
python main.py pool demo
```

面板上有独立的「股票池」页：`/api/pool` 读库、`/api/pool/refresh` 触发刷新。
采集由 `ext_data` 组件常驻承担，回测模式默认不装（那段行情是死的，
去抓"今天的涨停池"对回放没有意义）。

### 10.4 与策略的衔接

`score` 策略同时注册在**两条链路**上，共用同一套打分口径：

- 实盘：`app/core/strategy/score_strategy.py`（读 `composite_score` 因子，
  按 `entry_score` / `exit_score` 阈值开平仓）
- 回测：`app/strategy/score_strategy.py`（注册为 `"score"`，同样读因子）

> ⚠️ **两个 `score_strategy.py` 不是一个东西**：一个在 `app/core/strategy/`
> （实盘，跟 TaskRuntime 走），一个在 `app/strategy/`（回测，跟 backtrader 走）。
> 它们的**打分逻辑必须保持一致**，否则回测好看实盘难看。
> 改打分口径时两个文件都要过一遍。

### 10.5 网络不可用时会怎样

获取层（`app/data/marketx.py`）被代理/限流拦住时**降级而不是崩**：
拉不到就记一条警告、该项计入 `failed`，其余标的数据照常入库。
所以 `pool sync` 的输出里"成功 N 项"加几行失败原因是常态，不是报错。

想在没有网络的环境下验证逻辑，用 `pool demo` —— 它造的是合成数据，
验证的是**打分与排序链路本身**；数据获取那一段联网后单独用 `pool sync` 验证。
